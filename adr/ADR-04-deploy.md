# ADR-04-деплой

- **Статус:** принято
- **Дата:** 2026-09-15

## Контекст

Definition of Done требует, чтобы сервис был доступен из интернета и показывал
большой публичный репозиторий. Своей площадки нет: по README её выдают по
запросу. Деплой нужно подготовить так, чтобы он подошёл к любой площадке,
которая запускает контейнеры.

Сервис вызывает git, поэтому git должен быть на сервере. Пакет должен
оставаться встраиваемой библиотекой, а не превращаться в отдельное приложение.

## Решение

1. **Docker-образ** на `python:3.11-slim` с установленным git.
2. **Хост ставит пакет из wheel**, как в `examples/host-vendor`. Образ собирает
   тот же артефакт, что выпускается `make package`, и не использует исходники
   напрямую.
3. **Хост-приложение** лежит в `deploy/app.py`: монтирует `create_router`
   в режиме каталога клонов (ADR-02) и `mount_static_ui` под `/git`,
   отдаёт `/health`.
4. **Настройка через переменные окружения:** `GITPULSE_WORKSPACE` — каталог
   клонов, `PORT` — порт uvicorn. `GITPULSE_REPO_PATH` необязательно добавляет
   один фиксированный репозиторий рядом с реестром.
5. **Каталог клонов** монтируется томом, если площадка это позволяет.
   Если нет, ограничение называется в README.
6. **Учётные данные площадки** в репозиторий не попадают. Разворачивает сервис
   владелец площадки.

## Последствия

**Даёт:**
Один образ запускается на любой площадке с контейнерами;
Деплой проверяет ту же упаковку, которую получают хосты;
Сервис развёрнут так же, как его встраивал бы любой хост.

**Платим:**
Без постоянного тома клоны пропадают при перезапуске, и репозиторий нужно
подключать заново;
Первое подключение большого репозитория занимает минуты;
Место на диске растёт с каждым подключённым репозиторием.

## Критерии приёмки

1. `docker build` собирает образ, в котором доступен `git`. — проверено.
2. Запущенный контейнер отвечает 200 на `/health` и отдаёт UI на `/git/`. —
   проверено, включая реальное клонирование публичного репозитория изнутри
   контейнера и то, что подключённый репозиторий переживает пересоздание
   контейнера при сохранённом томе.
3. Внутри контейнера пакет установлен из wheel, а не из исходников. —
   проверено.
4. Через UI на живом URL подключается большой публичный репозиторий, и его
   данные видны. — **не выполнено**: подключение к площадке ещё не завершено,
   публичного URL нет. Образ и хост-приложение готовы и проверены локально;
   этот пункт закроется вместе с публикацией живого URL.
5. README описывает запуск и ограничения деплоя. — проверено.

## Дополнение: обратный прокси и SSL

- **Статус:** принято
- **Дата:** 2026-09-16

### Контекст

DoD требует сервис, доступный из интернета — по HTTPS. Своего домена нет,
площадка выдана по IP. Публичный удостоверяющий центр не выпускает
сертификат на голый IP-адрес: нужно доменное имя, на которое можно
проверить владение.

### Решение

1. **Обратный прокси — Caddy.** Единственное, что слушает 80/443, получает
   и продлевает сертификат Let's Encrypt сам, без ручного certbot-шага, и
   проксирует всё остальное на контейнер сервиса. Сервис наружу не
   публикуется напрямую.
2. **Источник доменного имени — `sslip.io`.** Публичный сервис, который
   резолвит домен вида `<IP-через-дефисы>.sslip.io` прямо в этот IP, без
   регистрации и настройки DNS. Формально это доменное имя, поэтому Let's
   Encrypt выпускает для него настоящий сертификат по HTTP-01 challenge —
   владеть доменом для этого не нужно, важно только, чтобы он резолвился
   на сервер, который отвечает на challenge. Как только появится
   собственный домен, замена — это только смена значения переменной
   окружения, без изменений в коде.
3. **Docker Compose** описывает пару контейнеров (сервис + Caddy) и именованные
   тома: для клонов (ADR-02) и отдельно для сертификата, чтобы оба
   переживали перезапуск.

### Последствия

**Даёт:**
Настоящий HTTPS без покупки домена и без ручного управления сертификатами;
Переход на купленный домен позже не требует правок кода.

**Платим:**
Ещё один контейнер и точка отказа перед сервисом;
Выпуск сертификата требует, чтобы порт 80 был доступен из интернета для
HTTP-01 challenge — если файрвол площадки его закрывает, сертификат не
выпустится.

### Критерии приёмки

1. Стек поднимается `docker compose` и оба контейнера отвечают на запросы.
2. HTTP-запрос редиректит на HTTPS.
3. Сертификат выпускается и обновляется автоматически, без ручных шагов.
4. UI и API отвечают через прокси так же, как при прямом обращении к
   контейнеру сервиса.

Пункты 1, 2 и 4 проверены локально (self-signed через встроенный CA Caddy,
поскольку настоящий сертификат требует реально доступного из интернета
домена). Пункт 3 (реальный Let's Encrypt) проверится вместе с публикацией
живого URL — тем же незакрытым пунктом 4 основного ADR-04.
